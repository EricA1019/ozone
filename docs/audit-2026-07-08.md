# Ozone Project Audit — 2026-07-08

> Full structural audit covering all source files, tests, documentation,
> configuration, and protocol compliance. 74 Rust source files, ~26,800 total
> lines, 5-feature build matrix, CI enforced.

---

## 1. Executive Summary

Ozone is a Rust CLI/TUI application that launches, monitors, profiles,
benchmarks, and evaluates local llama.cpp models. After Waves 1-4 of
structural debt remediation, the codebase has made substantial progress
from its earlier monolithic state. The App struct was cut from 73 to 36
pub fields, launcher.rs from 2,291 to 687 lines across 4 child modules,
profiling.rs split into mod.rs+workflow.rs, CLI handlers extracted to
commands/mod.rs, and the lite build (`--no-default-features`) now
compiles cleanly for the first time.

The project has 304 passing tests, 0 active bugs in BUGLOG, clippy-clean
default build, and a robust 5-matrix CI pipeline. The `ozone-mcp` crate
is still a 2,287-line monolith that has been planned for splitting but
not yet executed. 16 `#[allow(dead_code)]` suppressions remain, mostly
on fields reserved for future phases. `src/ui/mod.rs` at 1,672 lines
remains the single largest file in the active crate and serves as the
primary god-module for the TUI layer.

**Overall trend: Improving. The structural work (Waves 1-4) has moved the
needle from "needs major refactoring" to "core is solid, edges need
finishing." The remaining debt is concentrated and well-understood.**

## 2. What Is Working Well

### Build & CI Rigor
- **5-matrix clippy CI** (default, lite, full, mcp, no-ui) — catches
  feature-gate breakage before merge. The lite build fix (just committed)
  closes a longstanding gap.
- **Zero active bugs** in BUGLOG. All 22 recorded bugs fixed and moved to
  HISTORY. This is rare and reflects serious quality investment.
- **`make preflight`** passes consistently: clippy clean + 304 tests.
- **Two release profiles** (`release` and `release-lite`) with separate
  optimization strategies.

### Feature Gating
- The `eval` feature flag is cleanly plumbed through `Cargo.toml`,
  `lib.rs` module declarations, `ui/mod.rs` struct fields, and
  `launcher_loop.rs` match arms. 159 `#[cfg(feature = "...")]` gates
  total, with 67 complex gates (`any`, `all`, `not`).
- The lite build (`--no-default-features`) compiles error-free.
- `database` feature gates `rusqlite` dependency correctly.

### Test Coverage
- **4 integration test files** (`surface.rs`, `pre_split_snapshots.rs`,
  `tui_characterization.rs`, `eval_parser_fixtures.rs`) supplementing
  82 `mod tests` blocks across source files.
- **Surface tests** catch legacy-backend regressions (KoboldCpp, Ollama
  references should not reappear).
- **Pre-split snapshot tests** use real `ozone::*` imports, not
  duplicated logic — they stay in sync.
- **TUI characterization tests** exercise screen transitions without a
  real terminal.

### Bug Log Discipline
- BUGLOG has a clear ACTIVE/HISTORY structure, with commit hashes and
  dates on every entry. TDD fix plans are maintained separately.

### Constants & Named Values
- CLI defaults in `lib.rs` use named constants (`DEFAULT_LLAMACPP_URL`,
  `DEFAULT_LLAMACPP_PORT_STR`, `DEFAULT_CONTEXT_SIZE_STR`, etc.).
- `kv_cache_args()` in `processes.rs` is clean and well-documented.
- `launch_config.rs` has 21 named VRAM/RAM constants with rationale.

### Error Handling in Key Paths
- `lib.rs` has `#![cfg_attr(not(test), deny(clippy::unwrap_used, clippy::expect_used))]`.
  All 139 `.unwrap()` calls in the codebase are gated to test modules.
- `anyhow::Result` is used consistently across all fallible functions.

## 3. What Needs Work

### `src/ui/mod.rs` — 1,672 Lines
This is the single largest file in the `ozone` crate and acts as the
god-module for the entire TUI layer. It contains:
- The `App` struct (36 pub fields)
- `Screen` enum re-exports
- Key event handlers (`handle_splash_key`, `handle_monitor_key`,
  `handle_launcher_key`, etc.)
- The `App::new()` constructor
- All `build_effective_plan` logic
- All "flow" function dispatch
- 233 references to `Screen::` variants across 74 files

**Problem**: It has at least 4 distinct responsibilities (App state,
key dispatch, plan building, module re-exports). The flow functions
(e.g., `configure_hub_flow`, `configure_plan_flow`) should arguably
be extracted into `launcher_loop.rs` or a dedicated `dispatch.rs`.

### `crates/ozone-mcp/src/lib.rs` — 2,287 Lines
This is the largest file in the workspace and a known monolith. A
split plan exists (`docs/plans/monolith-refactor-plan.md`) targeting
7 files but has not been executed. The file mixes:
- JSON-RPC protocol handling
- Tool definitions and dispatch
- Sandbox management
- Journey building (23 `build_base_*` / `build_ozone_plus_*` functions)
- VTE screen parsing
- 571-line test module

### Dead Code Suppressions — 16 `#[allow(dead_code)]`
Concentrated in `src/eval_result.rs`, `src/theme.rs`, `src/scorers.rs`,
`src/catalog.rs`, `src/gate.rs`, `src/suites.rs`. Most have comments
like "Phase 3.3 wires this" or "reserved for future." While individually
documented, they collectively indicate unfinished work that may or may
not happen. Each suppression is a liability — if the phase never ships,
the dead code becomes permanent.

### CLI Dispatch — Inline EvalRun In `src/lib.rs`
The `Commands::EvalRun` dispatch arm in `src/lib.rs` (~100 lines) is
still inline, not extracted to `commands/mod.rs`. It builds the
`EvalRunConfig` struct inline with two nearly-identical branches
(for `no_manage_server` vs managed). This duplicates the struct
construction logic.

### `src/lib.rs` — 948 Lines
Still contains 6 inline handler dispatch arms (Bench, Sweep,
ThreadSweep, EvalRun, CreativeWrite). The CLI extraction completed
only 4 of 9 handlers. The `run()` function at ~250 lines is itself
too long.

### `src/bench_eval.rs` — 885 Lines (UI Module)
The largest UI child module. 18 `BenchEvalAction` enum variants.
Mixes rendering, action definitions, and helper functions. Would
benefit from splitting into render/action files.

### Documentation Staleness
- `.mex/context/decisions.md` has `last_updated: [YYYY-MM-DD]` — a
  placeholder that was never filled in.
- `docs/plans/structural-debt-remediation-plan.md` is written but
  was never populated with completed status (0 grep matches for
  "COMPLETE").
- `docs/archive/` contains ~600KB of ozone+ era documentation that
  is explicitly out of scope but still referenced by old plans.

## 4. Protocol Violations

### SRP (Single Responsibility Principle)
| Location | Violation | Severity |
|---|---|---|
| `src/ui/mod.rs` (1,672L) | God-module: App state + key dispatch + plan building + re-exports | **High** |
| `crates/ozone-mcp/src/lib.rs` (2,287L) | JSON-RPC + tool defs + sandbox + journey builder + VTE parser | **High** |
| `src/lib.rs` (948L) | CLI gateway + inline dispatch for 6 large handlers | Medium |
| `src/ui/bench_eval.rs` (885L) | Rendering + action enum + helpers | Medium |

### DRY (Don't Repeat Yourself)
- **EvalRunConfig construction** in `src/lib.rs` (lines ~770-830): Two
  nearly identical branches for `no_manage_server` vs managed, differing
  only in `manage_server`, `server_path`, and `model_name` resolution.
- **`kv_cache_args` pattern**: The `resolve_cache_type` closure logic
  for `OZONE_QUANT_K`/`OZONE_QUANT_V` env var fallback exists inline
  in the EvalRun dispatch. Similar env-fallback logic exists in
  `processes.rs` for server path resolution.

### Encapsulation
- **355 public items** (`pub fn`, `pub struct`, `pub enum`, `pub mod`)
  across `src/`. Some of these are forced by the `#[cfg(feature = "eval")]`
  gating pattern, but many (`pub` test functions, `pub(super)` helpers
  made `pub` for visibility chains) suggest the module boundary
  hierarchy isn't fully settled.
- Several flow modules in `src/ui/` use `pub use super::*;` which
  re-exports everything from the parent module, including internal
  helpers.

### Data-Driven Design
- **18 `BenchEvalAction` variants** in `src/ui/bench_eval.rs` are
  hardcoded. Each maps to an eval task. This duplicates the
  `EVAL_TASKS` registry in `src/eval.rs`. A new eval task requires
  changes in 2-3 files (registry, action enum, render match).
- **4 suites** (`HEALTH_SUITE`, `CANARY_SUITE`, `CODE_MICRO`,
  `FORMAT_MICRO`) are defined in `src/suites.rs` as `&[EvalTask]`
  slices. The 5th (`MATH_MICRO`) exists but is only wired in
  `SweepLevel::Full`.
- **Eval task display names** are duplicated between `cli_name()`
  and `report_label()` in `src/eval.rs` (EvalPreset enum).

### Open/Closed
- Adding a new eval task requires: (1) adding to `EVAL_TASKS` array,
  (2) adding a `BenchEvalAction` variant, (3) adding a render arm in
  `bench_eval.rs`, (4) adding a dispatch arm. This violates Open/Closed —
  the dispatch system is not extensible without modification.

### Naming Quality
- `src/processes.rs` is named for generic "processes" but contains
  exclusively llama.cpp launch/server management. The module violates
  its own name.
- `src/db.rs` is named generically but contains only benchmark result
  storage. It's a SQLite-backed repository for one concern.
- `src/policy.rs`, `src/gate.rs`, `src/preflight.rs` — these three
  modules have overlapping concerns (context validation, gating, policy
  enforcement). The boundary between them is unclear.

### Function Length
- The `run()` function in `src/lib.rs` is ~250 lines with 6 inline
  handler dispatch arms. Each arm is a self-contained handler that
  should be a separate function.
- `start_llamacpp()` in `src/processes.rs` is ~170 lines.
- `run_eval()` in `src/eval.rs` spans from line 579 to ~870 (~290 lines).

## 5. Risk Assessment

| Risk | Probability | Impact | Mitigation |
|---|---|---|---|
| **Eval task/action duplication** causes a new task to miss render or dispatch | Medium | Medium (silent omission) | Generate `BenchEvalAction` from `EVAL_TASKS` registry |
| **Feature gate combinatorics** (159 gates, 67 complex) cause untested build variant to break | Low | Medium (CI covers 5 variants) | Add a `cargo check` for each feature permutation in CI |
| **`ozone-mcp/lib.rs` monolith** slows development velocity on MCP tools | High | Medium | Execute existing split plan |
| **`ui/mod.rs` god-module** makes UI changes riskier than necessary | Medium | Medium-High | Extract flow dispatch into `launcher_loop.rs` or new `dispatch.rs` |
| **Dead code suppressions** for "future phases" never get wired | Medium | Low (suppressions are narrow) | Set a review date; if phase not started by N months, delete dead code |
| **`processes.rs` name/scope mismatch** leads to misplaced server logic | Low-Medium | Low | Rename to `llamacpp.rs` or `server.rs` |
| **No snapshot/approval tests for TUI rendering** allows visual regressions | Medium | Medium | Add `insta` or `ratatui` snapshot tests for each screen |
